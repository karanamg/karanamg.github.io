      Purchase orders & goods receipts

      Purchase orders from SAP S/4HANA and goods receipts from Manhattan Active WM, read through the Boomi API (GET /ws/rest/threeway/v1/purchaseorders and /goodsreceipts). The source data is simulated for this demo.

      How the 3-way match works

      A vendor invoice is only paid when it agrees with what was ordered (purchase order) and what was actually received (goods receipt). For every invoice line the Boomi process checks:

      Flow

      BrowserUpload PDF, watch the run, dashboard
      →
      Node gatewayReads the PDF text (pdf.js) and builds the invoice JSON. Holds the Boomi credentials.
      →
      Boomi API Service3WM Invoice Match API
      POST /ws/rest/threeway/v1/match
      [SUB] 3WM Get Purchase OrderSAP S/4HANA purchase orders → split → keep the PO named on the invoice
      [SUB] 3WM Get Goods ReceiptsManhattan Active WM receipts → split → keep receipts for the PO → combine
      3-way match engineCompares quantity, unit price and line value with tolerances
      DecisionApprove for payment, or route to the AP exception queue

      Systems of record

      SAP S/4HANA · ERPPurchase orders (header, lines, prices) via the standard OData API API_PURCHASEORDER_PROCESS_SRV.
      Boomi: SAP S/4HANA OData connector.
      Manhattan Active WM · WMSWarehouse receipts against each PO line, including partial deliveries.
      Boomi: REST connector to the Manhattan Active WM APIs.
      AP outcomeApproved invoices are released for payment in SAP; exceptions go to the AP exception queue.

      In this demo the SAP and Manhattan data are simulated by two Boomi subprocesses, [SUB] 3WM SAP S4HANA Purchase Orders (Simulated) and [SUB] 3WM Manhattan WMS Goods Receipts (Simulated), which hold the sample records in Message steps. Replace each Message step with the real connector call and the rest of the process stays the same. Boomi folder Companion/ThreeWayMatch.
